# Toolkit — the capstone toolchain

**Who needs this.** Every team, from Lab 19. The capstone's first non-negotiable
is "`git clone`, `make up`, working", and the second is a CI gate shown failing
on a deliberate break. No earlier lab had you write a Makefile, a compose file or
a gate for your own repository. `capstone/skeleton/` (it arrives with the
`capstone/` folder in the Week 6 zip) is a starter that already does all of it
for a placeholder rule; this guide takes you from that starter to
your own private repository, a runner for it, your Labs 16–18 code inside it,
and a rehearsed clean clone.

**Measured on:** Apple M4 Max, 36 GB, Docker Desktop 29.8 (linux/arm64), GNU Make
3.81, uv 0.7.15, git 2.50; base images `python:3.12-slim` and
`ghcr.io/astral-sh/uv:0.7.15` already present from week 1. Every command below was
run on the laptop or inside the course container (§6 says which), unless marked *(not run here)*.
Nothing on GitHub was run: no repository was created and no runner registered.

> **The minimum.** Copy the skeleton into a new private repository, run
> `make up && make test && make eval && make gate && make gate-break; make down`
> from a fresh clone, register a runner for the new repository, then replace the
> placeholder rule with your brief's, one `REPLACE` at a time, keeping the gate green.

---

## 1 · What the skeleton gives you

```
Makefile            .PHONY: help build up down lint test eval gate gate-break model-check clean
Dockerfile          uv builder stage -> python:3.12-slim runtime, non-root user, healthcheck on /health
compose.yaml        one service `app`, port 18960, a named volume for data, .env optional,
                    OLLAMA_HOST -> host.docker.internal:11434
pyproject.toml      fastapi, uvicorn, pydantic, pyyaml, httpx; dev: pytest, ruff (the course's pins)
uv.lock             generated by uv from pyproject.toml; commit both
app/rules.py        decide(): the placeholder rule ("approve if score >= threshold"), with latency and cost
app/main.py         GET /health, POST /decide, GET /metrics (cost and latency from the system's own log)
config/rules.yaml   the rule as data: threshold 0.70
eval/cases.jsonl    10 labelled cases, three of them at the threshold's boundary
eval/evaluate.py    the metrics gate.yaml names -> reports/eval.json
gate.yaml, gate.py  thresholds; PASS/FAIL per metric, exit 1 on any FAIL, 2 if it cannot evaluate
tests/test_rules.py 5 tests, including one that the evaluation set has a case just below the threshold
.github/workflows/  lint -> test -> eval -> gate -> "the gate can still fail", on [self-hosted, aip2]
docs/, reports/     what goes in each (README.md); the handover templates stay in capstone/handover/
```

Everything runs in Docker: a clean clone needs only git, make and Docker. Every
file says, in comments, what it is for and what to replace (`grep -rn REPLACE .`).
The skeleton's own `README.md` maps the six non-negotiables to files.

## 2 · Your repository, from the skeleton

Copy, do not clone the course repository: the capstone starts with its own history.
On the laptop (or in the course container, in your home folder; both work, §3.3):

```bash
cp -R capstone/skeleton/. ~/capstone-<team>   # "/." copies .github, .gitignore, .dockerignore too
cd ~/capstone-<team>
git init -b main && git add -A && git commit -m "Capstone skeleton"
git ls-files | wc -l                          # 25: if .github/workflows/ci.yml is missing, you copied without "/."
```

On github.com, as in Lab 8 ([`git-and-github.md`](git-and-github.md)): a **private**
repository named as the course channel specifies; your two teammates, the
instructor and the TA as collaborators. Then:

```bash
git remote add origin <the repo's URL>
git push -u origin main                       # (not run here)
```

Keep it **outside** the course repository's folder: a repository inside another
confuses both. Then the first clean clone (§6) and the first edit, in this order:
`compose.yaml` `name:` and `pyproject.toml` `name` (your team's), then
`make clean && make up`.

## 3 · A runner for the capstone repository

The Lab 12 runner is registered to your **course** repository. A repository-level
runner takes jobs from that one repository only: pushes to the capstone
repository would sit in **Queued** for ever. You need a runner registered to the
capstone repository. Two ways, both with the unchanged `labs/lab12/runner.sh`,
inside the course container (`make shell` in the course repository).

### 3.1 · A second runner beside the first (recommended)

`runner.sh` installs into `$HOME/actions-runner`. Give it a different `HOME` and
it installs, registers and runs a second, independent runner in another folder.
Checked here: with `HOME=/tmp/x`, the script resolves its folder to
`/tmp/x/actions-runner` (traced with `bash -x`; nothing was installed).

```bash
export CAP=/home/student/capstone-runner          # in the home volume: survives make down
HOME=$CAP bash labs/lab12/runner.sh install       # (not run here) downloads ~140-230 MB, checks the SHA-256
# GitHub: the CAPSTONE repo -> Settings -> Actions -> Runners -> New self-hosted runner;
# copy only the token from its ./config.sh line (it expires in an hour, works once)
HOME=$CAP bash labs/lab12/runner.sh register https://github.com/<org>/<capstone-repo> <token>   # (not run here)
HOME=$CAP bash labs/lab12/runner.sh run           # (not run here) a second terminal; "Listening for Jobs"
```

Both runners are named `aip2-<hostname>` and labelled `aip2`; that is fine, they
belong to different repositories. Each needs its own `run` terminal, and each
runs only when that terminal is open. At the end of the course, remove it with
`HOME=$CAP bash labs/lab12/runner.sh remove <token>` (the token from the runner's
*Remove* button on GitHub).

### 3.2 · Or: move the Lab 12 runner

Lab 13 is the last lab that uses the course repository's CI. After it, you may
re-point the one runner instead of keeping two:

```bash
bash labs/lab12/runner.sh remove <removal token from the COURSE repo's runner page>   # (not run here)
bash labs/lab12/runner.sh register https://github.com/<org>/<capstone-repo> <token>  # (not run here)
bash labs/lab12/runner.sh run
```

`register` passes `--replace`, but that replaces a runner of the same name on
GitHub; it does not reconfigure a folder that is already configured. Remove first.

### 3.3 · What the workflow assumes

| Assumption | Why |
|---|---|
| `runs-on: [self-hosted, aip2]` | `runner.sh` adds the label `aip2`; the job lands only on a runner with Docker, make and git |
| `COMPOSE_PROJECT_NAME: aip2skel-ci` (rename it) | CI's containers are a separate compose project: `make down` in CI never stops the stack you are demonstrating from |
| No bind mounts anywhere | the runner lives in the course container and talks to the laptop's Docker (Docker-outside-of-Docker). A `./reports:/app/reports` mount names a folder on the wrong machine. **Measured:** a file written in the course container, bind-mounted into a container started from it, showed an **empty** folder. The skeleton moves `reports/eval.json` through stdin and stdout instead |
| `! make gate-break` as a step | CI fails if the deliberate break stops failing: the evaluation set lost the cases that protect it |
| Private repository only | a self-hosted runner executes whatever a workflow says, with root-equivalent Docker access (`runner.sh`'s warning) |

The workflow file was checked as YAML (parsed, the step list read back) but has
**not run on GitHub**. Every `make` target it calls was run from a clean clone,
both on the laptop and inside the course container, which is where the runner
executes them. Your first push is its first run: watch the Actions tab and the
runner terminal together. A run stuck in **Queued** means the runner is not
running, or is registered to the other repository.

## 4 · Bringing your Labs 16–18 code across

Every Labs 16–18 file finds the repository root as "the nearest folder above me
with a `pyproject.toml`", then builds paths from it (`labs/lab16/server.py`,
`packs/<pack>/`, `packs.common`). The capstone repository has a `pyproject.toml`
at its root, so **keep the same relative paths** and the code runs unchanged.
Copy only what your system uses; move it into `app/` later, once tests cover it.

| From the course repository | Into the capstone repository |
|---|---|
| `labs/lab16/server.py`, `mcp_connect.py`, `contracts/<pack>.yaml` (and `client.py`, `contract_test.py` if you use them) | `labs/lab16/` |
| `labs/lab17/agent_common.py`, your agent (`agent_loop.py` or `sdk_agent.py`), `run_tasks.py` | `labs/lab17/` |
| `labs/lab18/defences.py`, `trust.py`, `harness_server.py`, `run_trust.py`, `attacks/<pack>.jsonl` | `labs/lab18/` |
| `packs/__init__.py`, `packs/common/`, `packs/<your pack>/` | `packs/` |

Then add the dependencies **with the course's pins**, which update
`pyproject.toml` and regenerate `uv.lock` in one step:

```bash
uv add mcp==2.2.0 "openai-agents[litellm]==0.22.3" litellm==1.83.0
git add pyproject.toml uv.lock labs packs && git commit -m "Labs 16-18 code and pins"
make build
```

`litellm==1.83.0` is pinned explicitly although `openai-agents[litellm]` pulls it
in: `agent_common.py`'s model routing was written against 1.83's behaviour, and an
unpinned resolve may pick a newer one. No `uv` on the laptop? Run the same `uv add`
inside the course container, in the capstone folder. Never `pip install`: it
changes one machine and not the lock.

**Measured** (all five steps, on a copy of the skeleton with the insurance pack):

| Step | Result |
|---|---|
| `uv add ...` (resolve, lock, install) | 5.8 s; the lock grows from 25 to 75 packages |
| `make build` | 16.8 s; image 283 MB → **561 MB** |
| `python labs/lab16/client.py --pack insurance as-openai`, in the container (`docker compose run --rm --no-deps -T app ...`) | the MCP server starts over stdio; 5 tools listed |
| versions in the image | mcp 2.2.0, openai-agents 0.22.3, litellm 1.83.0 |
| `make test` (ruff) on the starter files as shipped | **6 errors** (F401, F841) in the unfinished TODOs of `agent_loop.py`, `sdk_agent.py`, `defences.py` |

The last row is the trap: `make test` lints everything you copy. Copy your
finished files, not the starters, and delete what the system does not call.

**Wiring it into the system.** Keep `decide()`'s shape in `app/rules.py`: input in,
a `Decision` out with `latency_ms` and `cost_usd`. When the decision calls the
agent, fill `cost_usd` from Lab 17's `Usage` (tokens × the price table in
`agent_common.py`; $0 for a local model), so the evaluation and `/metrics` report
the system's own cost and latency.

## 5 · The local model, from inside compose

Ollama runs natively on the laptop, where it has the GPU. The skeleton's
`compose.yaml` already has the two lines that reach it:

```yaml
environment:
  OLLAMA_HOST: "${OLLAMA_HOST:-http://host.docker.internal:11434}"
extra_hosts:
  - "host.docker.internal:host-gateway"     # built into Docker Desktop; needed on Linux
```

`agent_common.py` reads the same `OLLAMA_HOST`. Check the path before you debug
anything else:

```bash
make model-check
# model-check: http://host.docker.internal:11434 answers; 15 models; gemma4:e4b-mlx present     (exit 0)
OLLAMA_HOST=http://host.docker.internal:9 make model-check
# model-check: nothing answers at http://host.docker.internal:9 (ConnectError). ...              (exit 2)
```

Both measured. The second is Lab 21's "model unreachable" drill: put it in `.env`
(copied from `.env.example`), `make down && make up`, and record what the system
does. On Linux, Ollama listens on 127.0.0.1 only by default and the container
gets `Connection refused`: see [`local-models-ollama.md`](local-models-ollama.md) §7.
Six briefs forbid data leaving the premises: for an egress proof inside your own
stack, Lab 15's `compose.airgap.yaml` is the pattern (an internal network and a
gateway); add it as a second service only when the brief needs it.

## 6 · The clean-clone rehearsal

The reviewers run your repository on a laptop that has never seen it. Rehearse
exactly that, on the teammate's laptop that has run it least:

```bash
git clone <your repo> /tmp/rehearse && cd /tmp/rehearse
time make up && time make test && time make eval && time make gate
time make gate-break; echo "exit $?"          # must be non-zero
git status --porcelain                        # must print nothing
make down
```

- [ ] `make up` ends with `up: http://0.0.0.0:18960/health`, and that URL answers
- [ ] `make test`: ruff "All checks passed!" and every test passed
- [ ] `make eval` prints the scoping document's section 3 metrics and the evaluation-set hash
- [ ] `make gate` prints `gate: PASS`
- [ ] `make gate-break` shows the change it made, then `gate: FAIL`, and make reports an error
- [ ] `git status --porcelain` is empty: nothing the commands did is left in the tree
- [ ] the times go into `reports/sprint_review.md`; anything that broke is fixed, committed, and the rehearsal repeated

**The skeleton's own rehearsal** (`git init`, commit, `git clone`, then each target;
the same image name and ports as shipped):

| Command | On the laptop | Inside the course container (where CI runs) |
|---|---|---|
| `make up` | 9.1 s (7.2–9.1 s over three runs; 13.4 s the very first build) | 6.7 s |
| `make test` | 0.9 s, ruff clean, 5 passed | 0.9 s, same |
| `make eval` | 0.4 s | 0.4 s |
| `make gate` | 0.4 s, PASS, exit 0 | 0.4 s, PASS, exit 0 |
| `make gate-break` | 0.5 s, FAIL (2 bounds), make exits 2 | 0.5 s, FAIL (2 bounds), exit 2 |
| `git status --porcelain` afterwards | empty | empty |
| `make model-check` | 0.6 s, model present | 0.6 s, model present |
| `make down` | 0.4 s | 0.4 s |

The image is 283 MB; a rebuild with no layer cache took 5.3 s (1.7 s of it uv
fetching and preparing 23 packages). Your system's numbers will be larger as soon
as `make eval` calls a model: the reference slice's `make eval` took 16–17 s for
20–22 cases.

## 7 · Traps the reference slice hit, and what the skeleton does about each

| Trap | What you see | Fix (already in the skeleton) |
|---|---|---|
| ruff writes a cache next to the code, which is root's in the image | `make test` fails with a permission error on `.ruff_cache` | `ruff check --no-cache` |
| pytest writes `.pytest_cache` the same way | a warning or failure on the cache directory | `pytest -p no:cacheprovider` |
| the `eval` target and the `eval/` directory share a name | `make: 'eval' is up to date.` and nothing runs (reproduced here with GNU Make 3.81 once `.PHONY` was removed) | `.PHONY: ... eval ...` lists every target |
| the gate passed a deliberate break | `gate: PASS` after you loosened the rule | boundary cases in the evaluation set. **Measured on the skeleton:** with the three boundary cases replaced by clear-cut ones (still 10 cases), threshold 0.70 → 0.60 gave `gate: PASS`; with them, `false_approvals` 2 and `accuracy` 0.8: FAIL. A test (`test_evaluation_set_has_a_case_just_below_the_threshold`) keeps one there |
| a deliberate break that edits tracked files | the demo leaves the repository broken, or a teammate commits the break | `gate-break` edits a copy inside a throwaway container; `git status` stays empty |
| a break that silently does nothing (the pattern no longer matches) | `gate: PASS`, and you think the gate failed to catch it | `gate-break` checks the copy differs and exits 3 with "the break did not apply" (measured) |
| bind mounts from inside the course container | the container sees an empty folder | named volume for data; reports via stdout/stdin |
| tabs in the Makefile | `Makefile:NN: *** missing separator.  Stop.` | recipe lines start with a TAB; set your editor not to convert them |

## Try it

From a fresh copy of the skeleton: change `BREAK` in the `Makefile` to set the
threshold to 0.69, run `make gate-break`, and explain the result from
`eval/cases.jsonl` (measured: FAIL, one false approval). Then change case `c09`'s
score to 0.30, keeping its label, and run it again (measured: PASS, although the
rule is broken). What does that tell you about the cases your own gate needs?

## If it goes wrong

| Symptom | Likely cause |
|---|---|
| `port is already allocated` on `make up` | something uses 18960: `APP_PORT=18961` in `.env` |
| `make up` hangs at "Waiting", then fails | the service did not become healthy: `docker compose logs app` |
| `make gate` says `CANNOT EVALUATE` (exit 2) | no `reports/eval.json` (run `make eval`), or `gate.yaml` names a metric `evaluate.py` does not produce |
| `uv sync --frozen` fails in the build | `pyproject.toml` changed without `uv lock`: run `uv lock`, commit both files |
| the CI run sits in Queued | the runner is not running, or it is registered to the course repository (§3) |
| `make model-check` exits 2 | Ollama is not running on the host, or (Linux) listens on 127.0.0.1 only |
| `git status` shows `reports/eval.json` | it should not: it is in `.gitignore`. Commit dated copies of runs you cite instead |
